# El aviso de "configuración de proyecto corrupta" nunca puede aparecer en uso real

**Caso general que se estaba revisando:** Fase 6 (persistencia e integridad) — probar la degradación real de `AppSettings` a nivel de proyecto (AC-028.4/TC-090), no solo a nivel global.
**Prueba específica armada:** Contra la app real:
1. Crear un override de proyecto real y válido vía el comando real (`set_project_app_settings`, parámetros `cwd` + `partialSettings`) para la carpeta de prueba — confirmado que el merge global+proyecto funciona bien (`corner` del proyecto pisa al global, el resto cae al global — PASA, sin bug ahí).
2. Corromper ese mismo archivo de proyecto en disco (JSON inválido).
3. Invocar `get_app_settings({ cwd })` directo — confirma degradación correcta: cae a la configuración global completa con `usedDefaults: true` (coincide exacto con el test unitario real de `app_settings.rs`, sin bug en el backend).
4. Recargar la app completa y verificar si el aviso visible (`session-panel__notice`, "No se pudo leer tu configuración guardada...") aparece en la pantalla previa a sesión, con esa misma carpeta corrupta como la última usada (confirmado por "Retomar `<esa carpeta>`" visible).
**Qué tronó:** El aviso **nunca apareció**, pese a que el archivo de proyecto de la carpeta recordada estaba genuinamente corrupto.
**Cómo tronó:** `initializeAppSettings()` (`App.vue:1431`) se invoca **una sola vez, dentro de `onMounted`** (línea 1506), y en ese momento llama `getAppSettings(chosenCwd.value)` — pero `chosenCwd` **todavía es `null`** en ese punto (se confirma por grep: las únicas asignaciones a `chosenCwd.value` ocurren dentro de `pickFolder`/`beginSession`/`resumeSession`, todas disparadas por una acción del usuario que ocurre *después* del montaje). El único `watch(chosenCwd, ...)` existente solo refresca el submenú de "sesiones recientes", no vuelve a llamar `initializeAppSettings()`. Resultado: la comprobación de "¿el archivo de proyecto es válido?" **siempre se ejecuta con `cwd: null`**, es decir, siempre revisa únicamente el archivo global — nunca el de un proyecto específico, sin importar qué carpeta elija o recuerde el usuario.
**Resultado obtenido:** `usedDefaults: true` confirmado por invocación directa del comando real; `appSettingsNotice` (el aviso visible) permaneció `null`/ausente en la UI real tras recargar con esa carpeta como la recordada.
**Evidencia:** Ejecución en vivo vía CDP + lectura directa de `App.vue` (líneas 1209-1210, 1431-1438, 1500-1507).
**¿Bloquea el Hito de QA en curso?:** No. Es un hallazgo real de Fase 6: el mecanismo de degradación en sí funciona perfecto (backend, merge, fallback), pero la mitad de su propósito declarado (avisar al usuario) es inalcanzable en la práctica para configuración de proyecto — solo funcionaría, por coincidencia, si el archivo *global* estuviera corrupto al momento de arrancar la app.

**Corregido:** `initializeAppSettings` gana un parámetro `cwd` (antes solo leía `chosenCwd.value`, `null` en el arranque) y se invoca de nuevo desde `beginSession`/`resumeSession` con el `cwd` real ya resuelto, antes de arrancar el proceso — el aviso ahora sí puede detectar configuración de proyecto corrupta. Además ganó idempotencia real: `appSettingsNotice.value` se recalcula desde cero en cada llamada (antes solo se *fijaba* si `usedDefaults`, nunca se *limpiaba*), evitando que quede pegado un aviso viejo al cambiar a una carpeta válida sin recargar la app. Ver `specs/correcciones-qa-gauntlet/plan.md` Hito 12.
